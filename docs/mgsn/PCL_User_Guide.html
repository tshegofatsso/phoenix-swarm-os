Phoenix-Command Language (PCL) User Guide

This support document explains how the Phoenix-Swarm-OS dashboard represents workflow activity through PCL. It includes its implemented output format, common operating procedures, governance conventions, and practical troubleshooting.

Important: In the supplied application, PCL is a generated operational log format. It documents workflow actions; it is not presently an interactive shell, parser, or automation interface. Do not treat a displayed command as evidence that an external action has occurred without checking the corresponding task record.

1. Purpose and scope

The Phoenix-Command Language provides a compact, human-readable way to present workflow activity within the Phoenix-Swarm-OS convening console. A PCL line communicates a responsible agent, a work item or partnership context, an action, and—when relevant—a dependency or urgency marker.

Where PCL comes from. The source defines pclLine(step, task) and buildConveneSequence(). The former selects a command style from workflow data; the latter orders the resulting lines into a convening sequence and appends a closing commit record.

2. Core concepts

Agents

Agents are named workflow owners, introduced with @. Examples in the supplied source include @THUSO for strategy and orchestration, @SIZWE for backend and infrastructure, and @NALEDI for community engagement.

Tasks

Tasks are work units, introduced with #. Their identifiers are domain-based, for example #G2 for governance and #C3 for community delivery.

Partnership contexts

Partnership-wide actions are introduced with $, such as $MGSN-FEWL-BBNC. This makes the scope immediately visible in logs and governance records.

Dependencies

An upstream dependency is shown with <~, indicating that a delegated task relies on a preceding task. Example: delegate #C3 -> @NALEDI <~ #C1.

4. Implemented command reference

delegate — assign a task

Use this format to show that a named task has been delegated to its primary responsible agent. The optional dependency clause makes an upstream prerequisite explicit.

delegate #<TASK_ID> -> @<AGENT_NAME> [ <~ #<DEPENDENCY_ID> ]

# Examples
delegate #G2 -> @THUSO
delegate #C3 -> @NALEDI <~ #C1

convene — record a partnership-wide convening action

Use this format for actions directed to the full partnership or an all-agent audience. The dashboard uses !critical when the action warrants special operational attention.

convene $<PARTNERSHIP> :: "<ACTION_DESCRIPTION>" [ !critical ]

# Example
convene $MGSN-FEWL-BBNC :: "Activate meeting cadence — monthly check-in (O1)" !critical

status — describe an agent-specific operational update

Use this format when the log needs to attribute a narrative update to an individual agent without assigning a new task ID.

status @<AGENT_NAME> :: "<STATUS_UPDATE>"

# Example
status @SIZWE :: "Deploy data collection tools in field (I2)"

commit — close a completed convening sequence

Use this format as the final record in a prepared convening sequence. It captures a concise, auditable summary of the sequence completed.

commit $<PARTNERSHIP> :: "<SUMMARY_MESSAGE>"

# Example
commit $MGSN-FEWL-BBNC :: "23 tasks delegated across 8 agents, 4 phases"

5. Operational how-tos

How to read a planned workflow sequence

  1. Identify the phase heading in the dashboard, such as Planning, Execution, Reporting, or Governance.
  2. Read the command verb first: delegate denotes task assignment, convene denotes a partnership-wide activity, and status denotes a narrative update.
  3. For a delegation, read the task ID, assigned agent, and any <~ dependency from left to right.
  4. Confirm execution in the underlying task or governance record. A PCL line is an operational log representation, not an independent proof of completion.

How to trace a dependency before beginning work

  1. Locate the task’s PCL line and check for <~ #TASK.
  2. Open the referenced task in the Task Registry and review its outputs and current status.
  3. Only progress the dependent work once its prerequisite output has been validated by the relevant owner.
  4. Record a new status update or governance note through the application’s approved recordkeeping process; do not rely on a manually copied console line alone.

How to flag a governance-critical action

  1. Confirm that the matter is partnership-wide and requires elevated attention, such as a formal committee convening or a time-sensitive compliance action.
  2. Use the convene structure with the correct partnership context and a clear action description.
  3. Apply !critical only when the workflow should visibly mark the action as urgent.
  4. For approvals, retain the separate voting record, notice, quorum evidence, resolution, and action register required by the governing policy.

How to close a convening sequence

  1. Review the generated steps for correct phase order, assignees, and dependencies.
  2. Confirm that every material action has an owner and that open risks are recorded outside the console in the appropriate register.
  3. Use a final commit summary that is factual, concise, and does not claim completion of actions that remain pending.
  4. Archive the sequence together with the related task, meeting, and governance records under your applicable document-control practice.

6. Governance and documentation standards

Do not overstate status. PCL language should distinguish between delegation, acknowledgement, and verified completion. A task remains subject to the evidence and approval requirements defined by the relevant MGSN, FEWL, BBNC, committee, or legal process.
PracticeRecommended convention
ClarityUse meaningful action text that identifies the activity, intended outcome, and relevant task reference.
OwnershipUse the registered agent identifier and retain the named primary and backup owners in the task record.
DependenciesState the direct prerequisite task only; complex dependency chains belong in the formal task register or project plan.
Audit trailPair PCL output with the underlying action register, meeting minutes, approvals, evidence, and version-controlled documents.
ConfidentialityDo not include personal data, credentials, confidential financial information, or unapproved legal conclusions in PCL descriptions.

7. Troubleshooting

The wrong agent is shown after a delegate line

Check the task’s primary assignment in the task data, then verify that the workflow phase and destination agent match. In the current source, pclLine chooses the task by phase and primary agent; ambiguous mappings should be reviewed in the task registry.

A dependency is absent even though the task has prerequisites

The current helper shows only the first dependency, using task.deps[0]. Consult the full task record for all dependencies. A future revision may render multiple dependencies in a structured command object.

A line says commit, but work is still open

Interpret the line as the close of a generated convening sequence—not as automatic verification that work is complete. Check the individual task records, approvals, and evidence before reporting completion.

A PCL command cannot be typed back into the app

This is expected in the supplied implementation. The dashboard renders PCL strings for visibility; it has no interactive parser or execution engine. See the future extensions section for a safe evolution path.

8. Recommended future extensions

The following are proposed enhancements, not features of the supplied source. They should be implemented only after suitable authorization, testing, access controls, and audit requirements are defined.

  • Represent commands as structured objects, for example { type: "delegate", taskId: "G2", assignee: "THUSO" }, then render the PCL string from that object.
  • Add a validation layer that returns clear success, warning, or error states before recording an action.
  • Link command effects to task state, agent load, and an immutable audit record.
  • Add controlled export, search, filtering, and copy functions for authorized users.
  • Implement a role-based approval step before any PCL command can alter workflow data.
Design principle: retain PCL’s concise, readable syntax while keeping approval, execution, and evidence controls explicit and separate.
